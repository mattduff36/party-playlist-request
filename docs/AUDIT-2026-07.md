# Codebase & Spotify API Audit — July 2026

**Product:** Multi-tenant Party DJ Request system — guests request Spotify tracks; DJs approve/reject; approved tracks go to Spotify queue/playlist; TV display shows now-playing.

**Scope:** Bugs, coding practices, performance, Spotify usage/guidelines alignment.

---

## Severity legend

| Level | Meaning |
|-------|---------|
| P0 | Can cause outages, quota bans, or data/security issues |
| P1 | High impact on reliability or UX at scale |
| P2 | Maintainability / medium performance debt |
| P3 | Polish / nice-to-have |

---

## P0 — Critical

### 1. No Spotify 429 / Retry-After handling in core client

**Where:** `src/lib/spotify.ts` → `makeAuthenticatedRequest`  
**Issue:** Only retries on 401 (token refresh). On HTTP 429, the error is thrown immediately with no backoff or respect for `Retry-After`. Concurrent live events + admin polling can amplify rate-limit storms.  
**Risk:** Failed playback/queue actions; risk of exceeding Spotify rate limits under multi-tenant load.  
**Fix:** Retry with exponential backoff when `Retry-After` is present (cap retries); surface 429 cleanly to callers. *(Applied in this initiative.)*

### 2. Aggressive Spotify status polling

**Where:** `src/hooks/useApiQueries.ts` → `useSpotifyStatus` (`refetchInterval: 15s`), plus spotify-watcher and display clients  
**Issue:** Each open admin session hits Spotify-backed status APIs every 15s. Multiple DJs/tabs multiply calls to `/me/player` and related endpoints.  
**Recommendation:** Increase interval when playback is idle; pause refetch when tab unfocused (React Query `refetchIntervalInBackground: false`); prefer Pusher/watcher push for track changes; coalesce watcher ticks server-side.

## P1 — High

### 3. Guest request rate limit is in-memory only

**Where:** `src/app/api/request/route.ts`  
**Issue:** In-memory IP-hash limits do not share across Vercel instances; Redis rate-limiter modules exist (`src/lib/redis/rate-limiter.ts`) but are not the single source of truth for song requests.  
**Risk:** Guests can exceed intended limits under multi-instance deploy; Spotify search can be hammered.  
**Recommendation:** Route guest submit + search through Redis/Upstash limiters in production.

### 4. Oversized page components

**Where:** `src/app/[username]/display/page.tsx` (~1800+ lines), `src/app/[username]/request/page.tsx` (~900+ lines)  
**Issue:** Hard to test, hydrate, and reason about; mixes data fetching, layout, and animation.  
**Recommendation:** Split into mood shell + feature components (now-playing, queue, QR, search, submit).

### 5. Inconsistent theming / purple leftover chrome

**Where:** `AdminLayout`, admin settings/display, auth reset, `not-found`, emails  
**Issue:** Intended Spotify green theme is incomplete; purple Tailwind utilities and email gradients create an inconsistent “generic SaaS” look and confuse brand.  
**Recommendation:** Stage Signal design system + mood presets (this initiative).

### 6. Missing legal/contact routes

**Where:** Landing footer links to `/privacy`, `/terms`, `/contact`  
**Issue:** Routes appear missing — broken links / compliance risk.  
**Recommendation:** Add minimal static pages or remove links until ready.

## P2 — Medium

### 7. Verbose Spotify request logging

**Where:** `src/lib/spotify.ts`  
**Issue:** Per-request console logging with tokens/timings adds noise and slight overhead in production.  
**Recommendation:** Gate debug logs behind `NODE_ENV !== 'production'` or a `SPOTIFY_DEBUG` flag.

### 8. Search caching gaps

**Where:** Search API routes  
**Issue:** Short-TTL cache for identical guest queries would cut Spotify Search quota significantly during parties.  
**Recommendation:** Cache popular query results 30–60s per event/user.

### 9. Dual rate-limit systems

**Where:** In-memory guest limiter vs Redis modules  
**Issue:** Cognitive and operational complexity; easy to leave holes.  
**Recommendation:** One abstraction with memory fallback for local dev.

### 10. Root layout font/theme mismatch

**Where:** `src/app/layout.tsx` (Inter + `bg-gray-50`), `globals.css` (Arial body)  
**Issue:** Conflicts with dark branded pages and intended design system.  
**Recommendation:** Unified CSS variables + distinctive fonts (Stage Signal).

### 11. TypeScript `any` in event settings / Spotify shapes

**Where:** Display/admin pages casting `(eventSettings as any)`  
**Issue:** Theme/mood fields can drift from schema.  
**Recommendation:** Tighten `EventConfig` and typed API responses.

## Spotify scopes & guidelines alignment

**Current scopes** (`src/lib/spotify.ts`):

- `user-modify-playback-state`, `user-read-playback-state`, `user-read-currently-playing`
- `playlist-modify-public`, `playlist-modify-private`
- `playlist-read-private`, `playlist-read-collaborative`
- `user-read-private`

**Assessment:** Scopes match features (playback control, queue, playlist, search via user/app token). No obvious over-scoping for current features. Existing users must reconnect after scope additions (already documented in code).

**Usage pattern summary:**

| Call | Typical trigger | Frequency risk |
|------|-----------------|----------------|
| `GET /me/player` | Status poll / watcher | High if 15s × N clients |
| `GET /me/player/queue` | Admin/display | Medium |
| `GET /search` | Guest typing | High without debounce/cache |
| `POST /me/player/queue` | Approve | Low–medium |
| Playback control | DJ actions | Low |

**Guidelines-aligned practices to maintain:**

1. Respect 429 + `Retry-After` (required).  
2. Debounce guest search (client) + cache (server).  
3. Prefer event-driven updates (Pusher) over tight polling.  
4. Do not poll Spotify from every guest device — guests should hit your API; only DJ/server talks to Spotify for playback.  
5. Keep scopes minimal; re-auth when adding scopes.

## Summary

The app is functionally solid for its core loop, but Spotify resilience and multi-instance rate limiting are the main production risks. UI inconsistency (purple vs green) and oversized client pages are the main product/maintainability risks. This initiative addresses design debt, mood theming, emails, and critical 429 handling; remaining items are tracked above for follow-up.
